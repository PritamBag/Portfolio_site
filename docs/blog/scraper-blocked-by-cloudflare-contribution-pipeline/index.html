Scraper Blocked by Cloudflare? We Built a Contribution Pipeline

Our web scraper worked locally but got Cloudflare 404 errors on the production server. Instead of fighting the block or buying a scraping service, I redesigned how WIIMO collects data - and the data got better.

Web ScrapingCloudflareData PipelineSystem DesignData QualityWIIMO

Our web scraper worked perfectly on our laptops. Then we deployed it to the production server, and Cloudflare blocked every request with a 404 error. This post is about the decision that came after: why I didn't try to bypass the block, why we didn't buy a paid scraping service, and how I redesigned data collection into a contribution pipeline - one where teammates collect data, the system checks it, and nothing goes live until a human approves it.

The product is WIIMO, a food transparency platform that answers one question about packaged food: what is it made of? You scan a barcode or search for a product and see its ingredients, flagged additives, nutrition facts, and an A-E health grade. As the lead engineer, I own WIIMO from data collection to deployment. And for a product like this, the data is the product - every grade a user sees is only as good as the ingredient list and nutrition table behind it.

The Original Plan: One Scraper on the Production Server

Retailers already publish product listings online, so we started with automation. We built our own web scraper rather than relying on anyone else's, because we wanted full control over what was collected and how clean it was. It opened product pages the way a browser does, gathered the details and images, and saved them. On our own machines it did exactly that. The plan was to run it on the production server on a schedule, with nobody needing to watch it.

Why Our Scraper Was Blocked by Cloudflare in Production

In production, the scraper collected nothing. Every request came back as a Cloudflare 404. The same code, asking for the same pages, was turned away. The difference most likely wasn't the code - it was where the requests came from. On our laptops, requests came from ordinary home and office connections. In production, they came from a cloud server in a data centre, which is exactly the kind of traffic bot protection is designed to stop.

Local success tells you the code works. It tells you nothing about whether the production environment will let it work.

The lesson we learned the hard way

The Options I Weighed

A blocked scraper looks like a technical problem, so the tempting answer is a technical workaround. But the real question was a product one: what is the most reliable way to keep a growing catalogue of trustworthy food data? I compared three options:

OptionReliabilityCost & dependencyControl over data quality
Make server traffic look like normal visitorsFragile - can break any dayOngoing maintenance; works against the site's own choiceSame as before - nothing checks the data
Pay for a third-party scraping serviceGood, while we keep payingRecurring cost; our core data depends on another companyLow - we get their output, not our rules
Collect locally, review centrally (chosen)High - collection runs where it already worksNo vendor; uses our own scrapersHigh - every item is checked before it goes live

The first option was an arms race we didn't want to be in. The second was tempting because it's fast to start, but it would have made the heart of WIIMO - its data - depend on a vendor's pricing, limits, and idea of what clean data looks like. For a product whose whole promise is trustworthy information, I didn't want to hand that over. So I proposed the third option.

The Key Insight: Separate Collecting Data From Trusting It

The question had been: how do we get the server to collect data? The better question was: does the server need to collect it at all? Collection already worked from our own machines. What the server was good at was storing data, checking it, and serving it to the website and the app.

So I split the job into two responsibilities. Collection moved to teammates' machines. Production became the gatekeeper: it receives contributions, checks them, and only publishes what a reviewer approves. That one change in where responsibility lives fixed the blocking problem - and, as it turned out, several problems we hadn't noticed yet.

What Is a Contribution Pipeline?

A contribution pipeline is a data pipeline where new data arrives as a suggestion, not as a change. Contributions wait in a queue, the system checks them automatically, and a person decides what goes live. It's the same idea as a pull request for code, applied to data. At a high level, every piece of WIIMO data now takes the same path:

StepWhat happensWhy it matters
1. CollectTeammates run our scrapers on their own machinesWorks where the server was blocked
2. SubmitData is sent to WIIMO as a contribution, signed with that person's own access keyWe always know who sent what
3. QueueIt lands in a pending queue - never directly in the live catalogueNothing unchecked reaches users
4. CheckThe system scores how complete it is and tags the imagesReviewers see what's missing at a glance
5. ReviewA reviewer, signed in with two-factor authentication, approves or rejects itA human decides what goes live
6. PublishApproved data becomes a product page on the website and the appUsers only see reviewed data

The Design Principles Behind It

Suggestions, not changes. Incoming data never edits the live catalogue directly. A bad batch costs a few clicks to reject instead of a cleanup job on production data.

Separate who proposes from who approves. Contributors and reviewers are different roles. Each contributor has their own revocable access key, every submission is recorded against it, and reviewers sign in with two-factor authentication - because approving data effectively decides what users read about their food.

Let machines do the boring checks. A human-in-the-loop pipeline only works if review is fast. The system scores each contribution for completeness - is there an ingredient list, a nutrition table, a front-of-pack photo? - and tags its images, so a reviewer opens a contribution already knowing whether it's ready.

Build for contributors you don't have yet. The pipeline doesn't care whether a contribution comes from a teammate or, one day, from a user. That was deliberate.

What Changed After the Switch

Collection scaled horizontally. In production, we could only ever have run one scraper on one server. Now every teammate's machine can run scrapers at the same time, all feeding the same queue. Adding capacity means adding a contributor, not upgrading a server.

Data quality went up. Review turned out to be fast, and it catches things no scraper would. Reviewers reject items that aren't food at all - retail listings mix in plenty of those - along with blurry photos, half-loaded pages, and incomplete records. An unattended scraper would have published all of it.

We stopped fighting bot protection. Collection runs from ordinary connections where it already worked, so there's no workaround to maintain and no vendor bill.

And it still grows. WIIMO's catalogue has passed 8,300 products and 31,000 images, with new data reaching the live site only after review.

The Trade-offs I Accepted

No design is free, and this one has real costs. Collection now depends on people choosing to run it, rather than a server running on its own. And every item passes through a reviewer, which means review capacity is the natural bottleneck as volume grows. I accepted both because the alternative - fully automatic data with nobody checking it - is a worse failure for a product people use to decide what they eat. The completeness scores and image tags exist precisely to keep that bottleneck small.

What's Next: Contributions From Users

Today, teammates are the contributors. The next step is letting users suggest products too - someone who can't find a product on WIIMO should be able to add it. Because the pipeline already treats every contribution as a suggestion that needs approval, opening it to users is an extension of the same design rather than a rebuild. The questions shift from "can we collect this?" to "how do we keep trust high as more people contribute?" - which is exactly the kind of question this architecture was built to answer.

Lessons for Anyone Building a Data Product

Test where you'll run, not just what you'll run. Our scraper was correct; our assumption about the production environment wasn't.

Don't outsource the part of your product that makes it valuable. A paid service would have solved collection, but it would also have taken control of our data quality. For WIIMO, that control is the product.

When automation fails, rethink who does the work before reaching for more tools. Moving collection to where it already worked was simpler, cheaper, and more scalable than any workaround.

Treat incoming data like incoming code. Suggestions go into a queue, someone accountable approves them, and there's a record of who did what.

Frequently Asked Questions

Why does a web scraper work locally but get blocked in production?

Bot protection like Cloudflare looks at where traffic comes from. Requests from a home or office connection look like a normal visitor; requests from a cloud server look automated, so they're far more likely to be blocked or answered with an error page - in our case, a 404.

Is a paid scraping service better than building your own scraper?

It's faster to start, but you trade control and independence for convenience. If data quality is central to your product, owning collection - and checking everything before it goes live - is worth the extra effort.

Doesn't human review slow a data pipeline down?

Only if reviewers do the machine's job. With automatic completeness scores and image tags, good contributions are approved quickly and attention goes only to the ones that need it.

Having our scraper blocked by Cloudflare felt like a setback at the time. In hindsight, it pushed WIIMO toward the architecture it needed all along: collection that scales with people, and trust that comes from review. You can see more of the work behind WIIMO on my projects page.
